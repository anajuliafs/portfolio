Overview

A shared visual language for Comgás's digital products. We mapped the interfaces of four products (Comgás Virtual, Smart Energia, Soluções and Quero Comgás), inventoried the components in use and turned what we found into a Figma library with tokens, 42 components and a governance model the Comgás team can run on its own.

Figma — Comgás Design System
01 — Challenge

Many products,
no shared source

Comgás runs several digital fronts at once: the customer self-service area (Comgás Virtual), the services store, the Smart Energia portal and the acquisition pages for new customers. Each had grown with its own screens, grids and visual decisions.

Without a shared library, the same needs were solved again and again. Teams duplicated components, added new colors and variables without a standard, and products drifted apart. There was also no clear way to decide what should become part of the system.

Besides the components, Comgás needed a way to keep the system consistent after the project ended.

Key Insight

Without someone responsible for the library, duplication comes back, even with a good set of components.

03 — Inventory

Seeing the system
as it was

Before designing anything, we inventoried what already existed in Comgás Virtual's mobile experience. Every screen was broken down into its components, and each component was logged with its modifiers, states, intent, usage and a link to the screen where it was found.

Then we placed similar pieces side by side. Buttons, cards, accordions, inputs, search fields, dropdowns and steppers each appeared in several versions solving the same problem. We also measured the AS-IS values of spacing, typography, radius, shadows and color, and noted a direction for each one.

The audit gave us evidence of the inconsistencies, and it became the starting point for the foundations and the component list.

04 — Foundations

Tokens that
carry meaning

The foundations are built in three layers of variables. Primitives hold raw values, semantic tokens describe intent (background, text, icon, border) and a responsive collection adapts typography, spacing and grid to each platform.

Designers don't pick hex values. They pick a purpose, like bg-danger or text-primary, and the token points to the right value.

05 — Components

42 components,
one behavior

Every component, from buttons and inputs to bottom sheets, date pickers and charts, uses only the system's variables. Each page opens with what the component is for and a short list of good practices, followed by the full variant set.

Components are shown in context, in app and desktop frames, so the team can see how the same piece behaves on each platform before using it.

06 — Governance

A system that
outlives the project

We wrote a governance guide (v1.0) that defines roles, principles, accessibility checks, criteria for adding components, a deprecation process and a monthly 30-minute health review.

We also recommended that Comgás name an Owner and a Backup for the library. This person doesn't need to be a design systems specialist. They need interest in organization, a systemic view and knowledge of Comgás's products.

The golden rule — before creating anything new

  1. ReuseCheck if an existing component already solves it.
  2. AdaptAdjust content or layout within the component.
  3. Add a variantExtend with a property or state.
  4. Add a variableOnly with alignment from the Owner.
  5. Create a componentThe last resort, when the need is real.

Approval flow

Need→Check existing component→Proposal→Owner review→Added to library→New version published
Principle

Reuse → Evolve → Standardize → Document. Only create something new when there's a real need.
